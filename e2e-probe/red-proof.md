## 撞到的四个真实问题

### ① 假绿：`expect.poll` 采到了过渡态（红向 B 不转红的真因）

首版判据是"`main` 文本长度变化了"：

```ts
await expect.poll(len).not.toBe(before);   // ❌ 恒绿
```

改点**已在的** tab 时，长度实测恒等（25242 → 25242），但判据仍绿。
机制：click 期间页面会短暂重渲染，poll 的**第一次采样**采到了那个长度差就立刻通过。

**结论：「某个量变了」不是好判据，「某个物在/不在」才是。**
长度类指标要配采样时序约束；可见性类是离散态，没有过渡态可钻。

### ② 依赖渲染时序的可见性同样不可靠

第二版拿 `#page-chat` 的可见性当判据，也红了。实测裸 `goto` 后 **4 秒内一直是
`display:none`**，换个等待策略又变可见 ⇒ 该元素的可见性由异步渲染时序决定。

**结论：先量、后写判据。** 判据选取必须来自对真实页面的多次观测，
且要挑**离散、稳定、与时序无关**的量。

### ③ 我凭记忆写错了断言（两次）

- `#hErrors` 被我写进「08-08 已删挂载点」清单 ⇒ 转红。实查：它是**活挂载点**，
  写端在 `static/hub/01-core-boot.js:538`，只在有启动异常时填 `innerHTML`。
  "我记得它被删了" ≠ "它不存在"。
- 第二次把「常态为空」也写死 ⇒ 又转红。`#hStale` 实际显示「需重启」，
  因为 `/health.code_stale=true`（主 checkout 5 条未提交⇒ 运行指纹与 HEAD 不符）。
  它是**如实反映**，不是坏了。

⇒ 第二版改成**一致性断言**（挂载点显示什么，必须由 `/health` 的哪个字段解释），
这比"常态为空"更强：任何环境下都恒真，真出问题时照样红。

⚠️ **不该把「健康态」写进断言**——健康态是环境变量，写死等于把 CI 的偶发状态
焊进用例。

### ④ API 先读原则（我因此报废了两条用例）

同一个文件里连错三次：`app.page()` 不存在、`locator.innerText()` 实为 `textContent()`、
`browser.getByRole()` 不存在（语义查询全在 `screen` 上，`browser` 只有 CSS/XPath
的 `locator()`）。

**结论：写测试代码前先把 `node_modules/**/dist/*.d.ts` 读完**，别照着 Playwright
的肌肉记忆写——e2e 有自己的 `App` / `Screen` / `Browser` 三件套。

## 本批撞到的四个新坑（按踩坑顺序）

### A. `toHaveCount(0)` 与 `toBeHidden()` 是两回事（本批最容易犯）

页面容器靠 `display` 切换，**节点始终留在 DOM 里**：

```
本机项目页可见 input:[按名称 / 路径过滤…]
切到本机项目后 getByPlaceholder('按名称 / 全名过滤…') 的 count 仍是 1（只是不可见）
```

⇒ 用 `toHaveCount(0)` 断言「另一页的控件不在」会**恒红**。
**规则：「DOM 里没有」用 count(0)、「在 DOM 里但隐藏」用 toBeHidden()，两种形态两种判据。**
（第一批的 `#ftTime` 是真被删除 ⇒ 用 count(0) 对；这里节点保留 ⇒ 必须 toBeHidden。）

### B. ⚠️ 可访问名 ≠ 可见文字（本批最隐蔽）

侧栏「资源」tab：可见文字 `资源`，而 **`aria-label="资源监控"`**。
a11y 规则 aria-label 优先 ⇒ 语义查询必须写 `{ name: '资源监控' }`，
写 `{ name: '资源' }` ⇒ 30s 超时后 `LOCATOR_NOT_FOUND`。

**为什么前面几条没暴露**：「总览」「本机项目」的 aria-label 恰好等于可见文字 ⇒ **侥幸能中**。
一旦某个控件的 aria-label 与文案不一致（中文里极常见），照界面文字写的判据整条失效。

> 已加元断言 `toHaveText(['总览','本机项目','GitHub 项目','资源'])` 把差异钉在用例里，
> 让后人一眼看到「界面写资源、查询得用资源监控」。

### C. 资源页**不适合**做 agent 步骤（框架的固有局限，不是配错）

`agent.act('点击「刷新」')` **每次超时**（119s → `TEST_TIMEOUT`）。
报告的cache 字段说明原因：

```
mode: agent-concluded, reason: end-mismatch, replayedActions: 1, totalActions: 1
```

回放了那一下点击，但**结束状态复核不通过** ⇒ 交接给 agent 重新接管 ⇒ 慢且贵。

根因：**资源页状态本质动态**（本机 Agent 随时启停，列表条数与 CPU/内存读数每次都变）。
docs/cache.mdx 明写「每次读数不同的文本不作为结束状态的证据」⇒ **回放永远 miss**。

> **修正上一轮的乐观结论：回放缓存不是万能的，目标页面状态越动态越不适合。**
> 该用例改为不经模型（直接点「刷新」），判据保留 ⇒ 零 token、1.32s。
> 真要让 agent 点这一页，得先给资源页一个稳定数据源（冻结/夹具）。

### D. 观测矛盾时，先怀疑自己的取样方式

同一个页面我观测到「两页各有可见过滤框」与「两页都没有可见 input」两个矛盾结论。
差别是：后者用 `document.querySelectorAll('main input')` —— 而过滤框**不在 `<main>` 内**。
⇒ 取证脚本本身选错容器也会造出假结论；**必须用页面容器 id（`#page-localprojects` 等）做交叉验证**。

## 扩量后的成本实测

| 场景（第几次跑） | 耗时 | 模型调用 | token | Cache |
|---|---|---|---|---|
| 全量 14 条（第 1 次） | 30.86s | 3 | 16.0k | 3 replayed · 1 missed |
| 全量 14 条（第 2 次，**实测非推测**） | 36.74s | 2 | 14.5k（47% cached） | 3 replayed · **1 missed** |

⚠️ **成本没有趋零**：连跑两次仍是 `1 missed`，每次 2 次模型调用 / ~15k token。
对比第一批那条**单步骤**用例（首次 22.5k → 回放 **0**）——
差异在于那条只有一步、录制完整，而全量里总有一条**回放不掉**。

**「跑一次就永久零成本」不成立**：只要有 miss，每次都要重新调模型。
稳定趋零的前提是**所有** agent 步骤都能回放，而这要求目标页面状态足够静态
（见 C：动态页面的回放永远 miss）。

# 追加二：合入 master 后的复现取证（2026-10-09 夜）

合入 master 后首次全量跑出现 **1 条失败**，是本批最重要的一次缺陷暴露。

## 失败形态：`agent` 报 passed，页面却没变

```
TEST: agent 能切到「本机项目」并看到本项目专有的过滤框   failed
  step: agent     passed  56433 ms   cache: {mode: missed, reason: no-entry}
  step: assertion failed  5036 ms
    expect.toHaveAttribute failed
    getByRole("tab", name: "本机项目")
    expected: aria-selected "true"
    observed: aria-selected "false"
```

即：**agent 步骤判定成功（passed），但页面实际仍停在「总览」**。

> **这条差点成为假绿，而拦住它的正是我当初刻意加的那层校验**
> （用例注释里写「agent 的 passed 来自模型判断，只有 locator 才是页面事实」）。
> 若只信 agent 的 verdict，那次就是绿的——**free池驱动的 agent 会误报成功**。

## 是否 flaky：未复现，样本不足

| 取证 | 结果 |
|---|---|
| 直接复跑 2 次 | 4/4、4/4（但走**回放**，回放掩盖随机性 ⇒ 证据无效） |
| `cache clear` 后**连录 3 次**（每次真调模型） | 4/4、4/4、4/4 |

⇒ **未复现**。诚实表述：**观察到 1 次「模型报成功但页面未切换」，重录 3 次未再现。
失败率 ≤ 1/4，但样本太小不足以定量，不能断言 flaky，也不能断言稳定。**

⚠️ 顺带修正一个取证错误：我最初用「复跑 2 次都过」当作"稳定"的证据——
**那两次是回放，模型压根没被调用**，等于什么都没验。
清缓存重录才是有效取证。**「跑了 N 次都过」必须先确认 N 次里有多少真的走了模型。**

## 由此确立的使用纪律

1. **agent 步骤后必须有与模型无关的 locator 断言**，否则模型误报成功即为假绿。
2. **不能把 agent 步骤当回归闸门**，只能当"辅助探索"。
   它既可能慢（动态页超时）、又可能误报成功（本次），还可能烧 token（miss）。
3. 真要用它做闸门，前提是三条同时成立：
   目标页面状态足够静态（否则永远 miss）+断言不依赖模型 +
   跑 `--strict-cache` 且接受"陈旧录制直接红"的严格度。
